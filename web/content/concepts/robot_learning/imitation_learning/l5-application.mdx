interview:
  answer: >-
    Imitation learning is learning a policy from demonstrations rather than from
    a reward signal. That difference in supervision is the whole reason it
    dominates real-robot work — reward design is fiddly and exploration on
    hardware is slow and sometimes destructive, so showing the robot the task is
    usually cheaper than specifying it. There are three broad families and they
    differ in what you copy. Behaviour cloning copies the actions directly,
    which makes it plain supervised learning; its weakness is that it trains on
    the expert's state distribution and gets tested on its own, so errors
    compound. DAgger fixes exactly that by having the expert label the states
    the learner actually visits, at the cost of needing an expert you can query
    online. Distribution-matching methods like GAIL match the state-action
    occupancy measure instead of conditional actions, which addresses the same
    problem without an expert oracle, but you can only estimate the policy's
    occupancy by rolling out, so you pay RL's sample complexity. And inverse RL
    recovers the reward that explains the demonstrations, which is the most
    transferable representation of intent but is under-determined — a constant
    reward explains any behaviour — so you need something like a maximum-entropy
    principle to pick among explanations. In practice I'd choose by what I
    actually have rather than by which is nicest: no simulator rules out
    anything needing rollouts, no queryable expert rules out DAgger, and reward
    labels or mixed-quality data open up offline RL, which unlike cloning can
    beat the average demonstration. The two limits worth stating up front are
    that imitation can't exceed the demonstrator, and it has no data for
    recovery because good experts never need to recover.
  followUps:
    - q: "When would you pick inverse RL over behaviour cloning?"
      a: >-
        When I need the intent to transfer, not just the trajectories. A reward
        function is a much more compact description of the task and stays valid
        under changed dynamics or new initial states, where a cloned policy
        would have to be recollected. So: new embodiment, changed environment,
        or a need to exceed the demonstrator. The costs are real though — the
        problem is under-determined, and most formulations have an RL loop
        inside every outer iteration, so it's expensive and finicky. For a
        fixed task on fixed hardware, cloning is almost always the better trade.
    - q: "How does offline RL differ from behaviour cloning on the same data?"
      a: >-
        Cloning imitates the average behaviour in the dataset. Offline RL uses
        reward labels to evaluate actions, which lets it stitch together good
        segments from different trajectories and exceed any single
        demonstration. That's a genuine capability gap. The price is
        distributional: value estimates for actions the dataset never contains
        are extrapolations and tend to be wildly optimistic, so every practical
        offline RL method adds some conservatism — constraining the policy to
        the data or penalising out-of-distribution values. With uniformly
        expert demonstrations and no failures, cloning is often the better
        choice; the more mixed the data quality, the more offline RL wins.
    - q: "Your cloned policy matches the expert on validation but fails on the robot. Walk me through it."
      a: >-
        First I'd check the split was per-episode, not per-timestep —
        consecutive frames are nearly identical, so a random timestep split
        leaks near-duplicates and makes validation loss meaningless. If the
        split is clean, then low action error with task failure is the
        signature of distribution shift: I'm measuring accuracy on the expert's
        states and the policy is failing on its own. Then I'd look at how it
        fails. Growing drift over the episode is compounding error, and I'd
        reach for chunking or recovery data. A repeatable failure at one
        specific point where demonstrations disagree is mode averaging, and I'd
        reach for a diffusion or discretised action head instead.
    - q: "If you had to double a policy's success rate, would you change the algorithm or the data?"
      a: >-
        Data, in almost every case I've seen. The consistent finding from Bridge
        Data onward is that broader, more diverse demonstrations move
        generalisation far more than swapping objectives on a narrow dataset.
        The exception is when there's a specific diagnosed failure the algorithm
        genuinely can't represent — obvious mode averaging is the clearest one,
        where no amount of extra data fixes an architecture that can only output
        a conditional mean.

## The triage question

Most interview questions here are disguised resource questions. Establish what
exists before recommending anything:

<Steps>
<Step title="What data do you have, and is it uniformly good?">
Uniformly expert → cloning. Mixed quality with rewards or success labels →
offline RL, which turns the failures into signal instead of discarding them.
</Step>

<Step title="Can you interact with the environment?">
No → GAIL and most IRL are unavailable regardless of their merits. Say so
explicitly; it is the constraint that decides.
</Step>

<Step title="Is the expert code or a person?">
Code → DAgger and privileged distillation are cheap and probably right. A person
→ labelling dominates, and you want chunking, expressive action heads, or
perturbation-and-correction collection.
</Step>

<Step title="Do you need to beat the demonstrator?">
If yes, no pure imitation method suffices. Say that plainly, then propose
imitation for initialisation followed by RL fine-tuning.
</Step>
</Steps>

<InterviewAnswer />

<Warning>
The most common way this question goes wrong is answering "imitation learning"
with a description of behaviour cloning and stopping. Naming the families,
saying what each one matches, and then choosing on available resources is a
much stronger shape — and it sets up every follow-up they were going to ask
anyway.
</Warning>
