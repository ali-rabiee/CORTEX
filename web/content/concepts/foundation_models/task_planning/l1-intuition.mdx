## The gap this is filling

Ask a robot to "clear the table" and something has to decide that this means
picking up each object, putting it somewhere, and possibly wiping afterwards.
That decomposition is commonsense knowledge — exactly what a language model has
a great deal of and a control policy has none of.

So the pattern is: instruction in, sequence of executable skills out, each skill
being something the robot already has a policy for.

<Intuition>
You have hired someone who knows how everything in the world works and has never
been in this building. They can tell you that a spill needs absorbing before it
spreads, and that you generally pick up the broken glass first.

They cannot tell you whether there is a sponge in this room, whether the cupboard
is locked, or whether you can reach the far corner. And they will confidently
say "get the sponge" anyway.
</Intuition>

## Grounding is the whole problem

<Figure src="/figures/saycan-grounding.svg"
        alt="Four candidate skills scored twice: by a language model for how useful they sound, and by a value function for whether the robot can execute them now. The product selects a skill that is both sensible and feasible and rejects one that sounds excellent but cannot be done."
        caption="The language model supplies one factor and the robot supplies the other. Neither is sufficient alone: usefulness without feasibility gives impossible plans, feasibility without usefulness gives a robot doing whatever it happens to be good at." />

<KeyIdea>
The language model knows what *would* help. It has no access to what this robot,
in this room, in its current configuration, can do. Grounding means supplying
that second factor from the robot — and it must come from the robot's own
perception and value estimates, because it changes at every step and no amount
of prompting can represent it.
</KeyIdea>

The cleanest formulation scores each candidate skill twice and multiplies:

$$
\text{score}(\text{skill}) = \underbrace{p_{\text{LLM}}(\text{skill} \mid \text{instruction})}_{\text{how useful it sounds}}
\times
\underbrace{p(\text{success} \mid \text{skill},\, \text{state})}_{\text{whether it is possible now}}
$$

A skill that sounds excellent but scores near zero on feasibility drops out.
A skill the robot can certainly do but that helps nothing also drops out. What
survives is the intersection, which is the plan you wanted.

## Two output formats

<Steps>
<Step title="A sequence of skill names">
"pick up sponge", "go to table", "wipe". Simple, easy to ground because each
name maps to a policy you can score, and limited: there is no way to express
"repeat until clear" or "if the drawer is shut, open it first".
</Step>

<Step title="A program">
Emit Python that calls perception and control APIs. Loops, conditionals, and
arithmetic now come from the language model, which is unusually good at writing
code because code is heavily represented in pretraining. The cost is that a
generated program can throw, hang, or call something that does not exist — so it
needs a sandbox and a carefully designed API surface.
</Step>
</Steps>

## Why open-loop planning fails quietly

<Warning>
A plan generated once assumes every step succeeds. When step three silently
fails — the grasp slipped, the object was not where it looked — steps four
onward execute against a world the planner is only imagining. Each subsequent
action compounds the divergence.

This is the same structure as compounding error in behaviour cloning, moved up a
level, and it has the same fix: close the loop. Feed execution outcomes back to
the planner as text — "grasp failed", "the drawer is now open", a human saying
"no, the other one" — and replan from what actually happened.
</Warning>

That makes **success detection** a load-bearing component, and in practice it is
usually the weakest one. A planner that replans on accurate feedback is robust;
a planner replanning on a success detector that reports failure as success is
worse than open loop, because it now confidently generates recovery plans for
problems that do not exist.

## What to be sceptical about

<Steps>
<Step title="The skill library is doing a lot of work">
Every one of these systems assumes a set of trained low-level skills that mostly
work. The planner is choosing among them, not creating capability. Demonstrations
of impressive high-level reasoning rest on a foundation someone else built, and
the hard robotics is largely in that foundation.
</Step>

<Step title="Long-horizon success rates are modest">
Even with grounding and feedback, chaining ten steps means ten chances to fail.
If each skill succeeds 90% of the time, the sequence succeeds about 35% of the
time — which is why these demos are usually a handful of steps long.
</Step>
</Steps>
