## The first result, and what it missed

<PaperCard refKey="huang2022zeroshot" />

Ask a large language model to plan "shave" and it produces something entirely
sensible and entirely unexecutable — free text at whatever granularity it
chooses, referring to actions no robot has. The fix here is a projection: embed
each generated step and snap it to the nearest skill in the robot's library.

<KeyIdea>
That solves **executability** — every step is now a real skill — and not
**feasibility**. The nearest admissible skill to "get a sponge" is "pick up
sponge", which remains impossible if there is no sponge. Feasibility is
state-dependent and changes every step, so it cannot come from a nearest-neighbour
lookup in a fixed list. Keeping those two words apart is most of the conceptual
work in this area.
</KeyIdea>

## Grounding as part of the decision

<PaperCard refKey="ahn2022saycan" />

SayCan's contribution is to stop treating feasibility as a post-processing step.
Score each skill by the language model's estimate of usefulness *and* by a
learned value function's estimate of success from the current state, and
multiply. A skill that sounds perfect and cannot be executed now scores near
zero and never gets proposed.

The reuse is elegant: with a sparse success reward, a skill's value function
*is* its success probability, so anything already trained to execute the skill
provides the grounding term for free.

## Closing the loop, and changing the output space

<PaperGrid>
<PaperCard refKey="huang2022innermonologue" />
<PaperCard refKey="liang2022cap" />
</PaperGrid>

Inner Monologue makes the planner reactive: success detections, scene
descriptions, and human corrections come back as text, so a failed grasp
produces a replan rather than a plan continuing against an imagined world. The
comparison against open-loop planning is the argument, and it is the same
argument as replanning versus open-loop execution one level down.

Code as Policies changes what the model emits. A flat sequence cannot express
"repeat until the table is clear" or "if the drawer is shut, open it first"; a
program can, and language models write code unusually well. The trade is that a
program cannot be multiplied by an affordance score — so grounding moves inside
the API, with primitives checking preconditions and raising messages the planner
reads.

## Grounding keeps moving earlier

</PaperGrid>

PaLM-E puts perception *inside* the planner: continuous sensor embeddings become
tokens in the language model's stream, so it reasons over the scene rather than
over a caption someone else wrote. ReAct gives the general form of interleaving
reasoning with acting so observations revise the plan mid-stream. SayPlan
replaces the flat textual world description with a 3-D scene graph the planner
can search selectively — necessary once the environment is a building rather
than a tabletop and no longer fits in a prompt.

<KeyIdea>
The arc has one direction: grounding moves from a filter applied after
generation, to information available during generation, to a structured
representation the planner reasons over. Filtering an unconditioned model wastes
its probability mass on proposals that will be zeroed; conditioning it properly
does not. That progression is worth being able to state, because it also
predicts where the area goes next.
</KeyIdea>

## What to be sceptical about

<Steps>
<Step title="The skill library is doing the heavy lifting">
Every system here assumes a set of low-level skills that mostly work, built by
other means. The planner selects among them; it does not create capability. An
impressive high-level demonstration rests on a foundation that is where most of
the robotics difficulty actually lives.
</Step>

<Step title="Horizons are short for arithmetic reasons">
Chained success is a product. At 90% per skill, ten steps succeeds about 35% of
the time. Replanning fixes this only to the extent that failures are detected,
which makes the success detector — not the planner — the usual cap on
performance.
</Step>

<Step title="Evaluation is small-sample and bespoke">
The same problem as the rest of real-robot research: few trials, non-standard
environments, and task suites designed alongside the method. The qualitative
capability is real; cross-paper rankings should be read as weak evidence.
</Step>
</Steps>
