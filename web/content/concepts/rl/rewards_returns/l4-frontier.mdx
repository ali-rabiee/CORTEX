## A guarantee, which is rare

<PaperCard refKey="ng1999shaping" />

Shaping had been folklore: add intermediate rewards to help learning, and hope
you have not changed the problem. This paper made it a technique.

$$
F(s,a,s') = \gamma\,\Phi(s') - \Phi(s)
$$

leaves the optimal policy unchanged for *any* $\Phi$ — and no other form does.

<KeyIdea>
The uniqueness half is what makes it usable. Existence says a safe option is
available; uniqueness says everything else is unsafe, so you never have to reason
case by case about whether a particular heuristic bonus is harmless. "It's only a
small bonus, it probably won't matter" is exactly the reasoning the theorem rules
out — a small residual per cycle is still unbounded over enough cycles.
</KeyIdea>

It is also unusual in that the guarantee is unconditional. A wrong potential
slows learning and cannot change what the optimal behaviour is, so encoding a
heuristic you are unsure about carries no correctness risk.

## Naming the failures

<PaperCard refKey="amodei2016concrete" />

Before this, "the agent did something weird" was a single undifferentiated
category. Separating it into reward hacking, negative side effects, scalable
oversight, and safe exploration is what lets a practitioner say which failure
they are looking at — and different failures have different fixes.

<Steps>
<Step title="Reward hacking">
The objective is satisfied in an unintended way. Fixed by changing what the
reward measures, not by penalising the specific exploit — which usually just
moves it.
</Step>

<Step title="Negative side effects">
The agent achieves the objective and damages something the reward does not
mention. Not a hacking problem: the reward is silent rather than wrong, and
adding a penalty for every possible side effect does not scale.
</Step>

<Step title="Safe exploration">
The behaviour that must be avoided must also be *learned about*. This is why
anything catastrophic belongs in a constraint layer rather than in the reward —
a penalty has to be experienced to be learned from.
</Step>
</Steps>

## Capability makes it worse

<PaperCard refKey="pan2022misspecification" />

The finding that changes how you should think about validation: a more capable
agent can score *higher* on the proxy and *worse* on the true objective.

<Warning>
The mechanism is that the proxy was validated over the behaviours a weaker agent
produced, and says nothing outside that region. A stronger optimiser explores
further and finds where the two diverge — because maximising the proxy is partly
maximising its error.

Worse, some of these appear as **phase transitions** rather than gradual drift. A
gradual degradation is visible in monitoring and can be caught; a transition
means the exploit becomes reachable only once the optimiser is strong enough,
so all your evidence comes from the regime before it existed. Testing a smaller
model provides no assurance about a larger one.
</Warning>

## Not writing the reward at all

<PaperCard refKey="leike2018rewardmodeling" />

If specifying a reward is the problem, learn it — from human comparisons of
behaviours, or from demonstrations.

<KeyIdea>
This relocates the problem rather than removing it, and the paper is explicit
about that. A learned reward is a model fitted to a finite set of comparisons, so
it is a proxy with its own out-of-distribution behaviour — and the argument about
capability finding the divergence applies unchanged.

The tell is in the practice: methods that optimise a learned reward almost always
include a penalty keeping the policy near the one that generated the training
comparisons. That penalty is an explicit acknowledgement that the learned reward
is only valid locally, which is the same structure as a trust region and for the
same reason.
</KeyIdea>

## What this means for a robot

<Steps>
<Step title="Sparse and true beats dense and approximate">
A sparse reward for genuine completion cannot be gamed the way a dense proxy can.
It converts a specification problem into an exploration problem, and exploration
has better-understood tools — demonstrations, curricula, hindsight relabelling.
</Step>

<Step title="Shape only potential-based">
Four lines, an unconditional guarantee, and it removes a whole failure class.
There is little reason to use any other form.
</Step>

<Step title="Constraints outside the reward">
A penalty is tradeable against the main objective by construction — an agent will
accept it if the reward is large enough. Anything that must never happen belongs
in a layer that cannot be traded against, which is the safety-filter argument
arriving from a different direction.
</Step>

<Step title="Measure the true objective independently">
Reward hacking makes the optimised curve go up. The only visible signal is a
separate measurement of what you wanted, judged by something the agent is not
optimising.
</Step>
</Steps>
