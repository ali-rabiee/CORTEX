interview:
  answer: >-
    An MDP is the tuple of states, actions, transition dynamics, reward, and a
    discount factor, with the Markov property saying the next state depends on
    the current state and action alone — the history adds nothing. That's what
    makes dynamic programming and every Bellman backup legitimate, so it's the
    assumption underneath essentially all of RL. The thing I'd emphasise is
    that the Markov property isn't a fact about the world; it's a claim about
    the variable you decided to call the state. The same physical system is
    Markov or not depending on what you recorded. A single camera frame of a
    moving object isn't Markov, because it fixes position and destroys
    velocity, so two situations that need opposite actions map to the identical
    state — and then no policy that's a function of the state can be optimal
    for both. Two stacked frames is Markov. Nothing about the physics changed.
    That reframing makes it an engineering question: what do I have to include
    so the state is a sufficient statistic? For a manipulator, joint positions
    and velocities, goal information, and often gripper and contact state.
    Frame stacking handles anything with finite memory extent. When the
    dependence is unbounded — a door you unlocked, something you saw inside a
    container — you need a statistic that summarises the whole history, and
    that's what a recurrent hidden state or a transformer context is
    approximating. Formally the right object there is the belief state, which
    is provably sufficient, but computing it needs the transition and
    observation models you don't have, so in practice you learn a statistic and
    accept that nothing guarantees it's sufficient. And on gamma — it looks
    like part of the problem and behaves like a hyperparameter. It sets the
    effective horizon at roughly one over one minus gamma, it scales the value
    function by the same factor, and raising it increases return variance. For
    50-step manipulation episodes I'd use 0.99; for long locomotion, 0.995 or
    higher, and expect to need a better advantage estimator to pay for it.
  followUps:
    - q: "How would you tell, from training curves, that your state isn't Markov?"
      a: >-
        The signature is inconsistency rather than slowness. If the same state
        appears with genuinely different correct actions, there's irreducible
        error the policy can't remove, so returns plateau at a mediocre level
        and the value loss flattens well above zero regardless of capacity or
        training time. The cheap confirmation is to add memory — stack a couple
        of frames, or append velocity — and see if the plateau moves. If it
        does, that was it. If the curve is just slow but still climbing, it's a
        different problem: exploration, reward scale, or optimisation.
    - q: "Isn't every real problem a POMDP? Why does the MDP formalism matter?"
      a: >-
        Practically, yes — full state is almost never observable on a real
        robot. The formalism matters for two reasons. First, it tells you what
        you're violating and therefore what to do: if the missing information
        has finite extent, augment the state and you're genuinely back in the
        MDP setting with all its guarantees. Second, the POMDP theory says the
        belief state is a sufficient statistic and the belief MDP is Markov, so
        the memory in your policy has a well-defined target. Without the
        formalism, "add an LSTM" is a superstition. With it, it's an
        approximation to a specific object, and you know why it might fail.
    - q: "You have a sparse success reward at step 200 and gamma is 0.99. Is that going to work?"
      a: >-
        Probably not on its own. At 0.99 the effective horizon is about a
        hundred steps and 0.99 to the 200th is around 13%, so the signal
        reaching the first action is weak but not zero — the harder problem is
        that random exploration has to hit the success state at all before
        there's anything to propagate. So I'd separate the two issues. For the
        horizon, raise gamma to 0.995 or higher and accept the variance cost.
        For the exploration problem, the real fixes are shaping, demonstrations
        to seed the buffer, or hindsight relabelling if the task is
        goal-conditioned — none of which are gamma problems.
    - q: "When would you deliberately use a gamma lower than the task horizon suggests?"
      a: >-
        When I want the variance reduction more than the far-horizon
        optimality. Discounting is also a regulariser: it shortens the credit
        assignment path, which stabilises bootstrapped value learning and cuts
        the variance of Monte Carlo returns. If the task genuinely only needs
        local decisions — a reactive controller with dense reward — a lower
        gamma trains faster and more stably, and the bias it introduces costs
        nothing you cared about. That's a bias-variance decision, and it's
        worth framing it that way rather than treating gamma as given.
  traps:
    - "Saying 'real problems aren't Markov' as if it were a limitation of the formalism. It is a statement about your state variable, and the formalism is what tells you how to fix it."
    - "Claiming a bigger network or more data will fix a non-Markov state. The error is irreducible — the same state has two different correct actions — so no amount of capacity removes it."
    - "Treating $\\gamma$ as a fixed constant to be looked up. It sets the horizon, the value scale, and the return variance simultaneously, and the right value depends on the episode length you actually have."
    - "Reaching for an LSTM whenever memory is mentioned. If the missing information has finite extent — velocity, acceleration — frame stacking is simpler, has no optimisation pathologies, and provably restores the Markov property."

## Reading the symptoms

Almost every MDP-level bug shows up as one of three signatures.

<Steps>
<Step title="Plateau insensitive to capacity → the state is not Markov">
Returns flatten at a mediocre level and the critic loss flattens above zero
regardless of network size or training time. Identical states with different
returns force the value function to predict their average, and the residual is
irreducible. Confirm by adding velocity or stacking frames and watching the
floor move.
</Step>

<Step title="Locally sensible, never finishes → $\gamma$ too low">
The policy does something reasonable for twenty steps and never reaches the
goal. Compute $\gamma^{T}$ for your episode length; if the terminal reward
arrives discounted to under a percent, it is not steering anything.
</Step>

<Step title="Unstable values, slow credit assignment → $\gamma$ too high">
The other end of the same knob. Value targets scale as $R_{\max}/(1-\gamma)$ and
return variance grows with the horizon, so 0.999 on a task that needed 0.99
buys instability for optimality you did not need.
</Step>

<Step title="Reward being maximised, task not being done → the MDP is right and the reward is wrong">
Not a Markov problem. The agent is doing exactly what you wrote. Read the
learned behaviour as a bug report on the reward function.
</Step>

<Step title="Then match the memory fix to the memory horizon">
Finite extent — velocity, acceleration, recent contact — is frame stacking, and
it provably restores the Markov property. Unbounded extent is recurrence or
attention, with no such guarantee. Reaching for the second when the first would
do is a common and costly mistake.
</Step>
</Steps>

into a thing you engineer. Everything else in the answer — frame stacking,
belief states, why an LSTM is an approximation to something specific — follows
from that one sentence.
</Warning>
