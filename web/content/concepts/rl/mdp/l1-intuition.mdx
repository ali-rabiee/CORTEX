## Five objects, and a promise

An MDP is the contract that says what kind of problem you are solving. It has
five parts:

$$
(\mathcal{S},\; \mathcal{A},\; P(s' \mid s, a),\; R(s,a),\; \gamma)
$$

states, actions, how the world responds, what you are paid, and how much you
care about later versus now. Every RL algorithm you will meet is defined
relative to this tuple, and every one of them breaks in a specific way when one
of the five is misspecified.

The promise is the fourth item's neighbour — the transition function depends on
$s$ and $a$ **only**:

$$
P(s_{t+1} \mid s_t, a_t, s_{t-1}, a_{t-1}, \ldots) = P(s_{t+1} \mid s_t, a_t)
$$

## Whose property is it?

Here is the part that most treatments bury, and that interviewers listen for.

<KeyIdea>
The Markov property is not a fact about the world. It is a claim about **the
variable you decided to call the state**. Change the variable and the same
physical system stops or starts being Markov.
</KeyIdea>

        caption="Same physics, same camera, two different state variables. The left one is not Markov; the right one is. Nothing about the world was fixed — only what was recorded." />

<Intuition>
Chess is the standard example and it is a good one: the board position is
enough, and how the pieces got there is irrelevant. But notice that this is
only true because someone chose to define the state as the full board. Define
it as "the position of my queen" and chess is emphatically not Markov.

So the question is never "is this problem Markov?" It is "what do I have to
include so that it is?"
</Intuition>

## Formulating a robot task as an MDP

<Steps>
<Step title="Choose the state so it is sufficient">
For a 7-DoF arm: joint positions *and* velocities, plus goal information. Adding
velocities is not a detail — with positions alone, the same configuration
appears while swinging in either direction and demands different torques. If any
task-relevant quantity is hidden (contact, occluded contents), you have a POMDP
and must add memory.
</Step>

<Step title="Choose actions at the level you can actually command">
Joint torques, joint velocities, or end-effector deltas. This decision sets what
the transition function has to model and how far ahead a single action reaches —
torques give the most authority and the hardest credit assignment.
</Step>

<Step title="Let the simulator be $P$">
You almost never write $P$ down. MuJoCo or Isaac is your transition function,
and the sim2real gap is exactly the statement that it is the wrong one.
</Step>

<Step title="Write a reward you would be happy to see maximised literally">
The agent optimises what you wrote, not what you meant. A distance-to-goal
reward with a success bonus is standard; every term you add is a new way to be
gamed.
</Step>

<Step title="Set $\gamma$ from the horizon you need">
Effective horizon $\approx 1/(1-\gamma)$. For 50-step episodes $\gamma = 0.99$
(horizon 100) is comfortable; for a 1000-step locomotion task it is too myopic.
</Step>
</Steps>

<Warning>
$\gamma$ looks like a property of the problem and behaves like a hyperparameter.
Lower it and the agent becomes short-sighted; raise it and returns have higher
variance, value estimates take longer to propagate, and bootstrapped methods get
less stable. There is no "correct" value to look up — pick it from the horizon
the task actually needs, then check whether the pathologies at that end of the
range have shown up.
</Warning>
